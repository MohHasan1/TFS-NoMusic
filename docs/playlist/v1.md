# Playlists — v1

A short note on how playlists work in the first version, and why it was built this way.

## What a playlist is

A playlist is a list of songs that a signed-in user makes and owns. The user
picks a name, and adds NoMusic tracks to it. Nothing here is admin-curated —
each user manages their own playlists.

This is different from **Libraries** (`libraries` + `nomusic-libraries`), which
are big collections that only admins can build.

## The collection

New collection: `playlists` (see `src/collections/Playlists.ts`).

| Field        | What it is                                                              |
| ------------ | ---------------------------------------------------------------------- |
| `name`       | Playlist title. Required.                                             |
| `slug`       | Made automatically from the name — on create and again whenever the name is edited. Read-only, cosmetic only. Playlists are addressed by `id`, so the slug has no uniqueness guarantee (duplicates are allowed). |
| `user`       | The owner. Set automatically to whoever created it. Cannot be changed later. |
| `description`| Optional free text.                                                  |
| Cover Image  | Upload only — `imageFile` (→ media) and `uploadedImageURL` (filled automatically from the upload). Optional. Simpler than Libraries, which also allows an external URL. |
| `visibility` | `private` (default), `public`, or `unlisted`.                        |
| `tracks`     | The songs, as an ordered list of links to `nomusic`.                 |
| `trackCount` | Number of songs. Kept in sync automatically. Read-only.              |

### Hooks (`src/collections/hooks/playlists.ts`)

- `assignOwnerBeforeValidate` — on create, sets `user` to the logged-in user.
- `generateSlugBeforeValidate` — turns the name into a slug on create, and re-runs when the name changes.
- `syncTrackCountBeforeChange` — sets `trackCount` to the number of tracks on every save.
- `syncUploadImageURLBeforeValidate` — from `src/collections/hooks/_shared.ts`
  (shared by Libraries, Users, Nomusic, Playlists); when a cover is uploaded,
  copies the media URL into `uploadedImageURL`.

There is no automatic cover (no Unsplash fetch, no generated art) in v1 — the
user sets it or the playlist has none.

## Who can do what

| Action | Rule                                                        |
| ------ | ---------------------------------------------------------- |
| Create | Any signed-in user.                                       |
| Read   | Admin, the owner, or anyone if the playlist is not private. |
| Update | Admin or the owner.                                       |
| Delete | Admin or the owner.                                       |

Read uses `playlistAccess.canRead` (`src/collections/access/playlist.ts`);
update/delete use the shared `isAdminOrOwnDoc`. How the three visibility modes
actually behave is written up in `docs/playlist/visibility.md`.

## Why the songs are a plain list (and not a join table)

The songs live directly on the playlist as a `hasMany` link to `nomusic`. We
did **not** make a separate "playlist songs" join collection like
`nomusic-libraries`.

Reasons:

- A playlist belongs to one person and is edited as one thing. There is no need
  to look up a single playlist entry on its own or share one entry.
- Song order is just the order of the list — reordering is one save, no extra
  sort column to manage.
- Reading a playlist is one document. With `depth`, the song links turn into
  full song objects. No join query.
- Fewer parts: no second collection, no cascade-delete worry, no cross-collection
  count hook.

The join-table approach (`nomusic-libraries`) makes sense for Libraries because
those are true many-to-many, admin-managed, and can be huge, and each link can
carry its own data (`sortOrder`).

### How big can a playlist get

- Up to ~500 songs: totally fine, no concerns.
- ~500–1000: still fine, saves take a few milliseconds. The admin UI list gets slow.
- Over ~1000, or if we want drag-reorder at scale, per-song data (added date, added by),
  a hard "no duplicate song" rule, or collaborative playlists — switch to a join
  collection then.

Note: Payload rewrites the whole song list on every save, so "add one song" costs
the same as saving all of them. That is cheap at these sizes.

Also: `hasMany` does not block the same song being added twice. If we want to
prevent that, dedupe the array in a `beforeChange` hook.

## How to read a playlist with its songs

Fetch the playlist with a `depth` — Payload replaces the song IDs with the full
song objects, keeping the playlist order. Access rules run automatically, so a
non-owner only gets a playlist that is public or unlisted.

```ts
import { getPayload } from "payload";
import config from "#payload-config";

const payload = await getPayload({ config });

// depth 0 -> tracks are ID strings
// depth 1 -> tracks are full Nomusic docs, in order
const playlist = await payload.findByID({
  collection: "playlists",
  id: playlistId,
  depth: 1,
});
```

Playlists are always addressed by `id` (the slug is cosmetic and not unique).
To list a user's playlists:

```ts
const { docs } = await payload.find({
  collection: "playlists",
  where: { user: { equals: userId } },
  depth: 1,
});
```

Pick only the song fields you need:

```ts
const playlist = await payload.findByID({
  collection: "playlists",
  id: playlistId,
  depth: 1,
  populate: {
    nomusic: {
      name: true,
      artist: true,
      duration: true,
      uploadedAudioURL: true,
      uploadedImageURL: true,
    },
  },
});
```

Note: the `defaultPopulate` on the `playlists` collection only applies when a
playlist is loaded as a relationship from somewhere else — not to a direct
`findByID`. Use `depth` / `populate` / `select` for that.

### Paging through songs in a big playlist

Do not use `depth` on the playlist. Read the ID list, slice it, then load that
page of songs — and re-sort, because `in` does not keep order.

```ts
const trackIds = playlist.tracks as string[]; // depth 0
const page = trackIds.slice(offset, offset + 50);

const { docs: tracks } = await payload.find({
  collection: "nomusic",
  where: { id: { in: page } },
  limit: 50,
});

const byId = new Map(tracks.map((t) => [t.id, t]));
const ordered = page.map((id) => byId.get(id)).filter(Boolean);
```

## Not in v1 (maybe later)

- Automatic cover image (Unsplash fetch, or art generated from the name / track covers).
- Slug field is there, but no public share pages built yet.
- Caching (`"use cache"` + revalidate tags) for playlists.
- A join collection for playlist songs.
- Blocking duplicate songs.

## Database

- Production is MongoDB — the `playlists` collection is created on its own, no
  migration needed.
- Local dev is SQLite — the table is pushed automatically the next time
  `payload dev` starts.
